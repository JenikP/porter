# Phase 1 — independent applications

Status: PASS for the independent web application milestone. Verified using `node scripts/launch-check.mjs`; see [acceptance-results.json](acceptance-results.json).

Implemented three standalone Customer, Driver and Porter Operations access experiences with registration where permitted, password recovery/reset, onboarding, authenticated workspace entry and logout. Customer supports personal/business registration. Admin has no registration or role selector. Driver uses the session's own profile ID; the selector exists only in the preserved demo. Customer/Driver navigation contains no Admin entry. Each app has separate Vite routes, ports, API proxy configuration and build output.

Files: `apps/{customer,driver,admin}-web/src/main.tsx`, their `vite.config.ts`, `apps/customer-web/src/styles.css`, `apps/customer-web/src/pages/{HomePage,BookingPage,AccountPage,Feedback,JobDetail}.tsx`, `apps/driver-web/src/{app,Documents,ActiveJob,OfferPanel}.tsx`, `apps/admin-web/src/{app,Sidebar,Drivers}.tsx`, `packages/app-session/{package.json,tsconfig.json,src/index.ts,src/session.tsx}`, `packages/mock-platform/src/react.tsx`, `scripts/{dev,init-launch,build-api,launch-check,vite-aliases}.mjs` (aliases is `.ts`), root/API package configuration and `.gitignore`. Other existing mutation screens now await asynchronous persistence. The API files listed in Phase 2 provide authentication required by this milestone.

Workflow proof: all three branded login screens rendered at desktop/mobile sizes; Customer/business and Driver registration created separate identities; Customer onboarding entered its own dashboard; Admin authenticated separately; wrong-role login was rejected; logout returned to sign-in. Driver onboarding and real private-file submission were approved by Admin before online access. Full booking/delivery/dispute and re-login were exercised across independent browser contexts. No browser runtime errors. Browser plugin was unavailable; bundled Playwright with Edge was used.

The existing Crisp Productivity palette and shared UI remain. A generated sign-in concept and final screenshots were visually inspected; the simple code-native route graphic intentionally avoids suggesting a live map. Final auth screens use flatter surfaces and comfortable responsive typography; controls and recovery links work.

Limitations/external dependencies: password delivery is explicitly a development simulator until a real email adapter is configured. Admin bootstrap uses server-only settings; local startup generates a private password in ignored `.env.launch`. No public admin provisioning exists. Native packaging and hosted deployment are later phase work; this PASS applies to the verified independent local web apps.
